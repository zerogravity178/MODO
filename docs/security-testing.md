# Проверка изоляции данных MODO

Проверка автоматическая: скрипт сам создаёт временные модули, записи и
изображения в двух аккаунтах, проверяет, что данные одного недоступны
другому, и удаляет всё созданное.

## Что нужно

- Два **существующих** аккаунта MODO с разными e-mail и известными паролями.
- Запущенный из папки проекта терминал (или двойной щелчок по файлу
  `Проверка безопасности.cmd` в корне проекта).
- Node.js и установленные зависимости (`npm install`, если ещё не делали).

Создавать аккаунты скрипт не умеет — это осознанно.

## Запуск

Двойной щелчок по `Проверка безопасности.cmd`

или в терминале:

```
npm run security:check
```

Дальше скрипт спросит четыре значения: e-mail и пароль для A, e-mail и
пароль для B. Пароль при вводе не отображается.

## Что произойдёт

1. Войдёт в оба аккаунта обычным способом — тем же, каким входит человек
   через форму `/login`.
2. Создаст в каждом аккаунте временный модуль с именем
   `Проверка безопасности A — <8 символов>` и по одной записи с картинкой.
3. Проверит 13 пунктов (таблица ниже).
4. Удалит созданное и проверит, что удалилось.
5. Покажет итог: `ПРОЙДЕНО` / `НЕ ПРОЙДЕНО` по каждому пункту.

## Список проверок

| № | Что проверяется |
|---|---|
| 1 | A читает собственный модуль |
| 2a | Чужой модуль не появляется в списке модулей A |
| 2b | Чужой модуль не открывается напрямую по UUID |
| 3 | A создаёт запись в своём модуле |
| 4 | A не может создать запись в модуле B |
| 5 | A не может изменить запись B — и отдельный вход под B подтверждает, что данные не изменились |
| 6 | A не может удалить запись B — и под B видно, что запись на месте |
| 7 | A загружает файл в свой модуль |
| 8 | A не может загрузить файл в модуль B |
| 9 | A не получает подписанную ссылку на файл B |
| 10 | A не может удалить файл B — и под B видно, что файл открывается |
| 11 | Файл не открывается без авторизации по публичному адресу |
| 12 | Короткая подписанная ссылка (1 секунда) перестаёт работать через 2 секунды |
| 13 | Временные объекты удалены полностью |

**Важно про пункт 12.** Он проверяет только сам механизм истечения — на
ссылке в одну секунду. Стандартный часовой срок жизни ссылок он **не**
подтверждает: это была бы отдельная проверка с ожиданием в час.

**Важно про пункт 11.** Публичный адрес проверяется отдельным
неавторизованным запросом, без всяких токенов, и не пересекается с
проверкой подписанных ссылок.

## Если тест прервался

Скрипт сохраняет список созданных объектов в
`.tools/security-check-state.json` и при следующем запуске сначала
попробует убрать их. Отдельная команда только для уборки:

```
npm run security:check -- --cleanup
```

Удаляется **только** то, что перечислено в этом файле, — то есть объекты
конкретного прогона. Ваши модули и файлы не затрагиваются.

Если уборка всё же не удалась, скрипт покажет, что именно осталось и где
это искать вручную (Table Editor и Storage по имени с префиксом
«Проверка безопасности»).

## Чего скрипт не делает

- Не использует `service_role` — только тот же anon-ключ, что и приложение.
- Не меняет схему базы, RLS-политики и код приложения.
- Не создаёт аккаунты.
- Не печатает пароли, токены и ключи. E-mail в выводе маскируются
  (`iv***@example.com`).

## Ручная проверка (если нужна)

Сценарии с `curl` остались ниже как справочник — на случай, если нужно
проверить что-то вручную, не глядя на вывод скрипта.

### Подготовка

1. Создайте два аккаунта: **A** и **B** (разные e-mail).
2. Под **A** создайте модуль «Тест A» с полями «Название» и «Картинка»,
   добавьте одну запись с изображением.
3. Под **B** создайте модуль «Тест B» с теми же полями, добавьте запись.
4. Выпишите идентификаторы:

   | Что | Как выглядит | Откуда взять |
   |---|---|---|
   | `MODULE_A`, `MODULE_B` | uuid | адрес `/m/<uuid>` |
   | `RECORD_A`, `RECORD_B` | uuid | кнопка правки / DevTools |
   | `IMAGE_B` | `uid_B/MODULE_B/field-….jpg` | в записи B поле картинки |

5. Получите `access_token` для A: DevTools → Application → Cookies →
   `sb-<project>-auth-token` (значение — JSON, поле `access_token`).

Дальше все проверки — **под A**.

### Запросы

```bash
URL="https://othvqwihvfmlipsnoodm.supabase.co"
ANON="<anon key из .env.local>"
TOKEN="<access_token аккаунта A>"

# вставка записи в чужой модуль
curl -s -X POST "$URL/rest/v1/records" \
  -H "apikey: $ANON" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -H "Prefer: return=representation" \
  -d '{"module_id":"MODULE_B","user_id":"uid_A","data":{}}'

# изменение чужой записи
curl -s -X PATCH "$URL/rest/v1/records?id=eq.RECORD_B" \
  -H "apikey: $ANON" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -H "Prefer: return=representation" \
  -d '{"data":{"f1":"взлом"}}'

# удаление чужой записи
curl -s -X DELETE "$URL/rest/v1/records?id=eq.RECORD_B" \
  -H "apikey: $ANON" -H "Authorization: Bearer $TOKEN"

# загрузка в чужой модуль
printf 'x' > /tmp/x.jpg
curl -s -X POST "$URL/storage/v1/object/modo-images/uid_A/MODULE_B/x.jpg" \
  -H "apikey: $ANON" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: image/jpeg" --data-binary @/tmp/x.jpg

# подписанная ссылка на чужой файл
curl -s -X POST "$URL/storage/v1/object/sign/modo-images/IMAGE_B" \
  -H "apikey: $ANON" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"expiresIn":3600}'

# публичный доступ без авторизации
curl -s -o /dev/null -w "%{http_code}\n" \
  "$URL/storage/v1/object/public/modo-images/IMAGE_B"
```

Признаки успеха: вставка, загрузка и подпись возвращают `403` /
`AccessDenied`; изменение и удаление возвращают `[]` (пустой массив), а
данные B не меняются; публичный адрес не отдаёт файл.

## Что делать, если пункт 8 НЕ ПРОЙДЕН

Скорее всего не применена миграция `supabase/migrations/005_security_hardening.sql`.
До неё Storage проверяет только папку пользователя (`{user_id}/…`), но не
владельца модуля во втором сегменте пути. Само приложение таким способом
файлы не загружает, но политика формально пропускает такую запись.

Примените `005` в Supabase → SQL Editor и запустите проверку снова.
